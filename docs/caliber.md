# 项目 B · CSV / xlsx 口径表

**每条都是判定句**：拿到一行数据或一个文件，能立刻判断"算不算、算多少、算哪个月"。

| # | 口径项 | 判定句 |
|---|---|---|
| 1 | 符号约定 | 支出记为**负数**、收入记为**正数**，全库唯一约定；符号来源为账单「收/支」列，**不靠金额正负推断** |
| 2 | 退款 | 退款金额记为正数（等同收入），**计入退款发生月**，不计入原交易月（理由：已生成报告不回溯重算，只还原「这个月实际花了多少」） |
| 3 | 转账 / 提现 / 理财申赎 | **先看交易对方，再看类别**：① 对方含「提现」「零钱充值」「转入」「本人」→ 内部划转，`category='转账'`，**不计收支**；② 对方是具体商户/个人且备注或商品说明为消费 → 由 `web_search` 按商户名判为对应消费类别（如「王姐煎饼摊」→餐饮），**计入支出**；③ 判断不了 → `category='转账'`、**不计收支**，并在报告「待确认」区列出明细，供人工修正 |
| 3b | 「转账」类别语义 | 枚举里的 `转账` **专指内部划转**（提现、零钱充值、本人账户互转），**不表示「用转账方式消费」** |
| 4 | 去重键 | `transaction_id` 取微信「交易单号」/ 支付宝「交易号」；与 `bill_id` 组合唯一 |
| 5 | 金额精度 | 保留两位小数，四舍五入（`ROUND_HALF_UP`），不截断 |
| 6 | 表头定位 | 含「交易时间」且含「金额」的行；其上方均为说明行，**不计入数据**。（`.xlsx` 不可硬编码行号，须按特征词定位） |
| 7 | 月份归属 | 按**交易时间**归月，不按到账或导入时间 |
| 8 | 「收/支」列映射 | `支出`→负、`收入`→正、`/` 及其他→按第 3 条参与判定 |
| 9 | `file_rows` 定义 | 表头之后的**非空数据行数**；说明行、表头行、空行不计 |
| 10 | 分类兜底 | `web_search` 返回 `AMBIGUOUS`/`NOT_FOUND` 时，`category` 置 `NULL`，报表归入「未分类」，**不得丢弃该笔交易** |
| 11 | net 计算口径 | `net = income + expense`；`category IN ('转账','理财')` 的交易入库、计入 `count_all`，**不计入 income/expense/net**，汇总放在 `uncounted` |
| 12 | 双重计算防护 | 内部划转（提现/零钱充值）会同时出现在微信账单和银行卡账单中，**只允许计一次**：判为 `转账` 不计收支，天然规避两平台重复计数 |
| 13 | `bills.period` 语义 | `period` 取**账单文件的起始月**（如 `2026-10-22~2026-11-22` 的文件取 `2026-10`）；**按月统计一律以 `transactions.occurred_at` 为准，不查 `bills.period`** |
| 14 | 跨月账单 | 一个账单文件可跨月，其交易按各自 `occurred_at` 归月；**不因文件跨月而拆分 `bills` 行**，也不允许同一文件重复导入两次（由 `UNIQUE(platform, period)` 拦住） |
| 15 | 校验基准分层 | **解析层**：`count_all` 与按「收/支」列的原始汇总，须与账单头部声明一致（如 129 笔 / 收入 6152.22 / 支出 -3709.54 / 中性 9865.50）；**业务层**：`query_db` 的 `income/expense/net` 按本口径表重算，**剔除转账后与解析层不相等属于正常**，两层不得互相校验 |

## 微信账单实测基准（2026-10-22 ~ 2026-11-22）

|---|---|

| 收入 | **7 笔 / 6152.22** |
| 支出 | **117 笔 / -3709.54** |
| 中性交易 | **5 笔 / 9865.50** |
| 表头位置 | 0-based 第 **17** 行（前 17 行说明） |
| 时间基准 | 文件第 14 行声明「所有时间均为 UTC+08:00」→ 存 `timestamp`，不做时区转换 |

**已知口径差异**：微信把「个人转账 2 元」算作收入（含在 7 笔里），按本表第 3 条③应判为「不计收支」。因此业务层 `income` = 6150.22，与解析层 6152.22 **不等属正常**（见第 15 条）。
